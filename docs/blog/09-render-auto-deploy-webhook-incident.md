# Render 자동배포가 갑자기 안 됐던 이야기

> **이 글은 초안입니다.** git 히스토리와 코드만으로 재구성 가능한 부분과, 실제로 겪었던 사람의 기억이 있어야만 채울 수 있는 부분을 구분해뒀습니다. `[ ]`로 표시된 빈칸은 발행 전에 채워주세요.

## 확인되는 사실

GitHub에 push한 커밋이 Render 대시보드의 Deploys 목록에 새 배포로 안 잡히는 상태가 있었다. 그리고 이걸 고친 뒤 검증한 흔적이 커밋으로 남아있다.

```
d886741  test: Render 자동배포 웹훅 재연결 테스트  (빈 커밋, 내용 없음)
```

이 커밋 자체는 아무 코드 변경도 없는 빈 커밋이다. `git commit --allow-empty`로 만든, "이 커밋이 push된 뒤 Render에서 새 배포가 자동으로 시작되는지"만 확인하려는 목적의 커밋이었다. 즉 GitHub 앱 연결(또는 웹훅)을 재연결한 뒤, 정말 자동배포가 되살아났는지 검증하는 절차로 이 빈 커밋을 썼다는 뜻이다.

## 빈칸

- [ ] **정확히 언제, 어떻게 이 문제를 알아챘나** — 배포했다고 생각했는데 실제 화면엔 옛날 버전이 떠 있어서 알았는지, Render 대시보드를 우연히 열어보다가 발견했는지
- [ ] **실제 원인이 무엇이었나** — 아래 세 가지 후보 중 어느 것이었는지 확인 필요
  - GitHub 쪽에서 Render GitHub App의 저장소 접근 권한이 해제되거나 범위가 바뀐 경우 (예: "All repositories" → "Only select repositories"로 바뀌면서 이 레포가 빠짐)
  - Render 쪽 웹훅 URL 자체가 무효화된 경우
  - 그 외 원인
- [ ] **끊긴 채로 방치됐던 기간이 실제로 어느 정도였나** — 커밋 로그상 2026-05-21(`ffc3a4e`)부터 2026-07-29(`c466cf1`)까지 약 2개월의 공백이 있는데, 이게 "개발을 잠시 쉬었던 기간"인지 "그 사이에도 개발은 했는데 자동배포만 조용히 끊겨서 반영이 안 됐던 기간"인지는 커밋만으로는 구분할 수 없음
- [ ] **재연결 시 실제로 어떤 화면/버튼을 눌렀는지** — GitHub의 `Installed GitHub Apps` 설정 화면이었는지, Render의 `Reconnect repository` 버튼이었는지, 둘 다였는지

## 재연결 및 검증 절차 (코드/커밋 근거 있음)

1. GitHub `Settings > Applications > Installed GitHub Apps`에서 Render 앱이 이 저장소에 대한 접근 권한을 갖고 있는지 확인
2. Render 대시보드 > 서비스 > Settings에서 저장소 연결 상태 확인, 끊겨 있으면 재연결
3. **빈 커밋으로 실제 검증** — `git commit --allow-empty -m "test: Render 자동배포 웹훅 재연결 테스트"` 후 push해서, Render에서 새 배포가 자동으로 시작되는지 확인 (`d886741`이 바로 이 커밋)
4. 그래도 안 되면 Render 대시보드의 "Manual Deploy"로 임시 우회

## 왜 하필 빈 커밋으로 검증했나

이건 확인된 사실을 근거로 설명 가능하다. 재연결 작업 자체가 "정말 됐는지 눈으로 확인하기 전엔 안심할 수 없는" 종류의 작업이었기 때문에, 실제 기능 변경 없이 "이 커밋이 배포를 트리거하는지"만 순수하게 테스트할 수 있는 빈 커밋을 택한 것으로 보인다. 실제 기능 커밋으로 검증했다면, 자동배포가 여전히 안 됐을 때 "기능 코드에 문제가 있어서 배포가 실패한 건지, 애초에 자동배포 트리거 자체가 안 된 건지" 원인이 섞여버렸을 것이다.

## 재발 방지 (내부 운영 문서에서 가져옴)

- 정기적으로(예: 월 1회) Render 대시보드에서 "최근 배포가 최신 커밋과 일치하는지" 육안으로 확인하는 습관
- GitHub 조직/저장소 권한 설정을 변경할 일이 있으면, 변경 직후 반드시 자동배포가 여전히 되는지 확인
