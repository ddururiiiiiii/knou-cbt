# Render 자동배포가 갑자기 안 됐던 이야기

## 문제

배포/마이그레이션 사이클을 손에 익히려고, 연습 삼아 커밋(`6c89b73`)을 main에 push했다. 그런데 Render 대시보드의 Events 탭을 열어보니 이상했다. **마지막 배포가 `0d89471`**로 찍혀있었는데, 이건 그로부터 몇 달 전, Phase 0/1 작업(CSP, Sentry, robots.txt, 개인정보처리방침)을 시작하기도 전의 커밋이었다.

즉 그동안 만들었던 Phase 0/1(버그 수정, CSP, Sentry 연동, SEO)과 Phase 2(PDF 기출문제 추출 파이프라인) 관련 코드가 **몇 달간 실제 운영 서버에는 한 번도 반영되지 않은 채로** 있었다. GitHub에는 커밋이 다 올라가 있고, 로컬/개발 환경에서는 잘 동작하는 걸 여러 번 확인했으니 "당연히 배포도 됐겠지"라고 생각하고 있었는데, 실제 운영 서버는 몇 달 전 버전에 멈춰있었던 것이다.

## 원인

Render는 저장소별로 개별 웹훅을 등록하는 방식이 아니라, **GitHub App을 저장소에 설치하는 방식**으로 자동배포를 연결한다. GitHub의 `Settings > Applications > Installed GitHub Apps` 목록을 확인해보니, Render 앱이 아예 목록에 없었다. GitHub App 연결 자체가 어느 시점엔가 끊겨 있었던 것이다.

정확히 언제, 왜 끊겼는지는 로그로 남지 않아 확신할 순 없지만, 이 저장소의 이름이 한동안 `KNOU_CBT`와 `knou-cbt` 사이를 오갔던 이력과 무관하지 않을 가능성이 있다. 저장소 이름이 바뀌면 GitHub App의 접근 권한 범위가 재확인되지 않고 조용히 빠지는 경우가 있기 때문이다.

## 해결

1. Render 대시보드 → `knou-cbt` 서비스 → Settings 탭 → Build & Deploy 섹션에서 GitHub 저장소 연결을 **해제한 뒤 다시 연결(재인증)**했다. 이 과정에서 GitHub App의 저장소 접근 권한이 다시 부여됐다.
2. 재연결이 정말 됐는지 확인하려고, 실제 기능 변경 없는 빈 커밋을 만들어 push했다.

   ```bash
   git commit --allow-empty -m "test: Render 자동배포 웹훅 재연결 테스트"
   ```

   이 커밋(`d886741`)이 push된 직후 Render Events 탭에 자동 배포가 즉시 트리거되는 걸 확인했다. 실제 기능 커밋으로 검증했다면 "배포가 실패한 게 코드 문제인지, 애초에 트리거가 안 된 건지" 원인이 섞였을 텐데, 빈 커밋으로 "트리거 자체가 되는지"만 순수하게 확인할 수 있었다.
3. 정상화를 확인한 뒤, 밀려있던 실제 커밋들도 순차적으로 반영되는 걸 확인했다.

## 재발 방지

- 저장소 이름을 다시 바꾸면 GitHub App 권한이 또 끊길 수 있다는 걸 알게 됐으니, 이름 변경은 가급적 피하거나 변경 직후 반드시 자동배포를 재확인한다.
- push 후 가끔 Render Events 탭에서 실제로 자동배포가 도는지 육안으로 확인하는 습관을 들이기로 했다. "커밋을 올렸다"와 "배포가 됐다"는 별개의 사실이라는 걸 몇 달치 공백을 겪고 나서야 체감했다.

## 교훈

- 로컬/개발 환경에서 잘 동작하는 걸 확인했다고 해서 운영 서버에도 반영됐다고 착각하면 안 된다. 배포 파이프라인은 "확인하지 않으면 끊겨 있어도 아무도 모르는" 조용한 실패 지점이다.
- PaaS(Render)의 자동배포는 GitHub App 설치라는, 저장소 설정과는 별개의 권한 체계 위에서 동작한다. 저장소 이름 변경, 조직 권한 변경처럼 GitHub 쪽에서 뭔가를 건드릴 때마다 이 연결이 여전히 살아있는지 확인하는 습관이 필요하다.
- 재연결이 "됐다"는 걸 확신하려면 실제 기능 코드가 아니라 순수하게 "트리거되는지"만 검증할 수 있는 최소 단위(빈 커밋)로 테스트하는 게 원인 분리에 유리했다.
