# PostgreSQL 한글 정렬 버그 잡은 이야기

## 문제

학과 목록, 과목 목록 화면에서 이름순 정렬이 이상했다. 가나다순을 기대했는데, 눈으로 보기엔 순서가 뒤죽박죽이었다. 처음엔 "정렬 기준 컬럼을 잘못 잡았나" 의심했는데, 확인해보니 정렬 기준 자체가 잘못된 경우도 있었다. 예를 들어 시험 목록은 이름이 아니라 `ORDER BY e.id`로 정렬되고 있어서, 애초에 의미 있는 정렬이 아니었다.

이름으로 정렬하고 있는 화면들도 문제였다. `ORDER BY d.department_name`처럼 지극히 평범한 쿼리인데도 한글이 기대한 순서로 안 나왔다.

## 원인

PostgreSQL(정확히는 Supabase가 기본으로 설정한 로케일)에서 텍스트 정렬은 데이터베이스의 collation(정렬 규칙) 설정을 따른다. 로케일이 한글을 "가나다순"으로 정렬하도록 맞춰져 있지 않으면, 문자열은 시스템 로케일이나 유니코드 코드포인트 기준으로 정렬되면서 사람이 기대하는 가나다순과 어긋나는 결과가 나올 수 있다.

## 해결

각 매퍼 XML의 정렬 조건에 `COLLATE "C"`를 명시적으로 추가했다.

```sql
-- Before
ORDER BY d.department_name

-- After
ORDER BY d.department_name COLLATE "C"
```

과목/시험처럼 정렬 기준이 여러 컬럼인 경우도 전부 같은 방식으로 맞췄다.

```sql
ORDER BY d.department_name COLLATE "C", s.subject_name COLLATE "C", e.year DESC, e.id
```

`COLLATE "C"`는 로케일에 의존하지 않는 바이트 순서(바이너리) 정렬이다. 언뜻 "가나다순 정렬"과는 거리가 멀어 보이는 이름이지만, UTF-8로 인코딩된 한글은 코드포인트 순서와 실제 가나다 순서가 일치하기 때문에, 로케일에 의존하는 애매한 정렬 규칙보다 오히려 `COLLATE "C"`로 명시적인 바이트 순서 정렬을 강제하는 편이 예측 가능하고 의도한 결과(가나다순)를 안정적으로 얻을 수 있었다.

시험 목록처럼 애초에 이름 정렬이 아니었던 곳은 `ORDER BY d.department_name COLLATE "C", s.subject_name COLLATE "C", e.year DESC, e.id`처럼 "학과 → 과목 → 최신 연도순 → id"로 정렬 기준 자체를 다시 설계했다.

## 교훈

- 텍스트 정렬 문제는 애플리케이션 코드가 아니라 DB의 로케일/collation 설정에서 비롯되는 경우가 많다. 쿼리 문법 자체는 틀린 게 하나도 없는데 결과만 이상하다면, 정렬 기준 컬럼의 collation을 의심해봐야 한다.
- 관리형 DB(Supabase 등)를 쓰면 서버의 로케일 설정을 직접 건드릴 수 없는 경우가 많다. 이럴 땐 애플리케이션 쪽 쿼리에서 `COLLATE`를 명시적으로 지정하는 게 가장 확실하고 이식성 있는 해결책이다.
- 정렬 버그는 눈에 잘 안 띈다. 데이터가 적을 땐 우연히 맞아 보이다가, 데이터가 늘어나면서 뒤죽박죽인 게 드러나는 경우가 많아서 초기에 발견하기 어려운 종류의 버그였다.
