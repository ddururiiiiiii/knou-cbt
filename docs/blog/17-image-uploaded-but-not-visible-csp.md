# 이미지는 저장됐는데 화면엔 안 보이는 이유

## 문제

문제 등록 화면에서 이미지를 첨부하고 저장하면 500 에러가 났다. 처음엔 multipart 용량 제한 문제(YAML 들여쓰기 오류로 20MB 설정이 무시되던 별개의 버그)를 고쳤는데도 증상이 남아있었다. 겉으로 보이는 증상은 비슷했지만, 파고들어 보니 원인이 **총 세 겹**이었다 — 하나를 고치면 다음 레이어가 드러나는 식으로 순차적으로 발견됐다.

## 원인 ① — Supabase Storage RLS 정책 위반 (진짜 원인이 로그에 안 남고 있었다)

이미지 업로드를 처리하는 `ExamQuestionStorageService`의 Supabase Storage 호출부(`WebClient` 기반)가 `.block()`으로 응답을 기다리는데, 여기서 예외 처리가 전혀 없었다. Supabase가 403(`new row violates row-level security policy`)을 돌려줘도 `WebClientResponseException`이 그대로 위로 튀어 올라가 그냥 500 에러 화면으로 떨어졌고, **진짜 원인이 로그에도 화면에도 전혀 남지 않았다.**

먼저 이 예외를 구체적으로 잡아서 상태 코드와 응답 본문을 로그와 화면(플래시 메시지 — 이것도 지금까지 템플릿에 렌더링하는 부분 자체가 없어서 같이 추가했다)에 노출하도록 고쳤다. 그러자 진짜 원인이 드러났다 — Render에 등록된 `SUPABASE_KEY`가 **anon(익명) 키**였는데, Supabase 프로젝트의 Storage RLS 정책은 `notice`(공지사항) 버킷에만 INSERT를 허용하고 있었다. 문제 이미지가 올라가는 `exam` 버킷은 애초에 anon 키로 쓰기가 막혀 있었던 것이다.

**해결**은 Render의 `SUPABASE_KEY` 환경변수를 anon 키에서 **`service_role` 키**로 교체하는 것이었다. 이 엔드포인트는 관리자 전용(백엔드에서만 호출되는) 경로라, RLS를 완전히 우회해도 안전하다고 판단했다. 다만 `service_role` 키는 RLS를 무시할 수 있는 매우 강력한 권한을 가지므로, **절대 프론트엔드 코드에 노출되면 안 된다**는 전제가 깔린 선택이다.

이 수정은 코드가 아니라 Render 대시보드의 환경변수 값만 바뀐 것이라, git 히스토리에는 아무 흔적도 남지 않는다. 커밋에는 "원인을 로그에 드러내는 예외 처리"만 남아있고, 실제 근본 수정(키 교체)은 운영 환경에만 존재한다 — 이런 종류의 변경은 코드 리뷰만으로는 절대 재구성할 수 없기 때문에, 운영 문서에 따로 기록해두지 않으면 나중에 완전히 잊힌다.

## 원인 ② — CSP `img-src`에 Supabase 도메인 누락

RLS 문제를 고친 뒤엔 업로드와 저장은 성공했는데, 이번엔 문제관리 화면과 미리보기에서 이미지가 깨진 아이콘으로 보였다. CSP의 `img-src` 지시문이 이렇게 돼 있었다.

```
img-src 'self' data: www.google-analytics.com;
```

`*.supabase.co` 도메인이 허용 목록에 없어서, 브라우저가 이미지 로드를 CSP 위반으로 조용히 차단하고 있었다. 업로드(서버 ↔ Supabase 통신)는 CSP와 무관하니 성공했지만, 화면 표시(브라우저 ↔ Supabase 통신)는 CSP의 영향을 그대로 받는다 — 그래서 "저장은 되는데 화면엔 안 보이는" 정확히 그 증상으로 나타났다.

```
img-src 'self' data: www.google-analytics.com https://*.supabase.co;
```

`img-src`에 도메인을 추가하는 것으로 해결했다. (이후 로컬 업로드 미리보기를 위해 `blob:`도 추가로 허용했다.)

## 원인 ③ — 부가적인 UX 문제

하단 저장 버튼을 눌러 폼 전체를 제출(페이지 리다이렉트)하면, 저장 후 항상 스크롤이 최상단으로 리셋되는 불편함이 있었다. `sessionStorage`에 스크롤 위치를 저장해뒀다가 페이지 재로딩 시 하단 저장 버튼 위치로 자동 복원하도록 고쳤다.

## 교훈

- "이미지가 저장됐는데 안 보인다"는 증상 하나가, 사실은 서로 완전히 다른 계층의 원인(백엔드의 RLS 권한 문제, 브라우저의 CSP 차단)이 겹쳐서 만들어진 것이었다. 하나 고쳤다고 끝난 게 아니라, 그 다음 레이어에서 또 다른 원인이 기다리고 있었다.
- 외부 API(Supabase Storage 등) 호출에 예외 처리가 없으면, 진짜 원인이 로그에도 화면에도 전혀 안 남고 그냥 500으로 뭉개진다. 구체적인 예외 타입을 잡아서 상태 코드와 응답 본문을 드러내는 것만으로도 디버깅 시간이 크게 줄었다.
- 새로운 Storage 버킷을 추가할 때는 RLS 정책과 접근 키 권한을 기존 버킷과 동일하게 맞춰야 한다 — 자동으로 상속되지 않는다. 그리고 외부 이미지 도메인을 쓰는 기능을 추가할 때마다 CSP `img-src`도 같이 업데이트해야 한다는 걸 체크리스트에 넣게 됐다.
- 근본 수정이 코드가 아니라 배포 플랫폼의 환경변수(키 교체) 안에서 이뤄지는 경우, 그 사실 자체를 운영 문서에 남겨두지 않으면 나중에 "왜 됐지?"를 아무도 설명할 수 없다. 코드는 "원인을 드러내는 로직"만 보여줄 뿐, 실제 해결책은 코드 밖에 있었다.
