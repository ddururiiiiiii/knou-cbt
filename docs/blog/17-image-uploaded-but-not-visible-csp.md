# 이미지는 저장됐는데 화면엔 안 보이는 이유

> 처음엔 "CSP + Supabase RLS(Row Level Security) 이중 원인"이라고 메모해뒀던 소재였다. 그런데 실제로 코드를 다시 훑어보니, 이 프로젝트에는 RLS 관련 코드/설정/주석이 전혀 없었다. 실제 원인은 **CSP `img-src` 설정 누락**과 **서버 쪽 예외 처리 미흡**, 이렇게 다른 두 겹이었다. 소재를 정정해서 기록한다.

## 문제

문제 등록 화면에서 이미지를 업로드하면 Supabase Storage에는 파일이 정상적으로 올라갔다. 그런데 정작 그 이미지를 써야 하는 화면(문제 미리보기, 답안 확인 화면 등)에서는 이미지가 깨져서 안 보이는 경우가 있었다. "업로드는 됐는데 왜 안 보이지"라는, 저장 계층과 렌더링 계층 사이에서 원인을 찾아야 하는 전형적인 증상이었다.

## 원인 ① — CSP `img-src`에 Supabase 도메인이 빠져있었다

CSP 정책을 처음 설정할 때 `img-src`는 이렇게 돼 있었다.

```
img-src 'self' data: www.google-analytics.com;
```

Supabase Storage의 퍼블릭 URL(`https://*.supabase.co/storage/...`)이 허용 목록에 없었다. 브라우저는 CSP 위반을 조용히 처리한다 — 이미지 태그의 `src`가 정책에 안 맞으면, 에러를 화면에 띄우는 대신 그냥 이미지를 안 그린다(깨진 이미지 아이콘만 남는다). "CSP 도입 후 버튼이 안 눌리던 문제"와 원인 계열이 완전히 같다 — CSP는 위반을 "조용히" 처리하기 때문에 증상만 봐서는 원인을 짐작하기 어렵다.

해결은 `img-src`에 Supabase 도메인을 추가하는 것으로 끝났다.

```
img-src 'self' data: blob: www.google-analytics.com https://*.supabase.co;
```

(`blob:`은 이후 커밋에서 로컬 업로드 미리보기 기능을 위해 추가로 허용했다.)

## 원인 ② — 업로드 실패가 500으로 튀거나, 실패 메시지가 화면에 안 보였다

CSP를 고친 뒤에도 "가끔 이미지 업로드가 그냥 500 에러로 실패한다"는 별개의 문제가 남아있었다. Supabase Storage로 파일을 올리는 `WebClient` 호출이 실패하면 `WebClientResponseException`이나 `WebClientRequestException`이 던져지는데, 기존 코드는 `catch (IOException e)`만 잡고 있어서 이 예외들이 그대로 흘러나가 500 에러 화면으로 떨어졌다.

```java
try {
    // Supabase Storage 업로드 (WebClient)
    ...
} catch (IOException e) {
    // WebClientResponseException, WebClientRequestException은 여기서 안 잡힘
}
```

또한 업로드 실패 시 에러 메시지를 flash attribute로 설정만 해두고, 정작 화면 템플릿에서는 그 메시지를 렌더링하는 부분이 빠져있어서 "뭔가 실패한 것 같은데 왜 실패했는지 사용자는 알 방법이 없는" 상태이기도 했다.

두 가지를 같이 고쳤다 — 예외 처리 범위를 넓혀서 Supabase 관련 예외도 적절한 에러 응답(400)으로 변환하고, flash attribute로 넘긴 에러 메시지가 실제로 화면에 표시되도록 템플릿도 손봤다.

## 교훈

- "이미지가 저장됐는데 안 보인다"는 증상 하나가, 사실은 서로 무관한 두 개의 원인(브라우저의 CSP 차단 vs 서버의 예외 처리 미흡)이 겹쳐서 만들어진 것이었다. 증상이 하나라고 원인도 하나일 거라고 가정하면 안 된다는 걸 다시 배웠다.
- 레이어별로 디버깅 순서를 나누는 게 도움이 됐다 — 먼저 "파일이 실제로 스토리지에 있는가"(저장 계층), 그다음 "브라우저가 그 URL을 실제로 요청하는가, 요청했는데 막혔는가"(네트워크/CSP 계층), 마지막으로 "서버가 업로드 자체를 제대로 처리하고 실패 시 사용자에게 알려주는가"(애플리케이션 계층) 순으로 나눠서 확인하니 두 원인을 각각 명확히 분리할 수 있었다.
- 소재를 정리해둘 때 "그럴듯하게 들리는 원인(RLS)"을 실제로 코드에서 확인하지 않고 메모만 믿었다면, 있지도 않은 원인을 마치 있었던 것처럼 쓸 뻔했다. 기록은 나중에 다시 검증하지 않으면 스스로도 믿게 되는 부정확한 정보가 될 수 있다는 걸 이번 글을 쓰면서 느꼈다.
