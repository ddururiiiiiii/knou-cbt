# 가져오기 기능, 어디까지 엄격하게 검증해야 할까

## 1단계 — 엄격했다 (그리고 바로 터졌다)

엑셀로 문제를 일괄 업로드하는 기능의 초기 파서는 형식이 맞는다는 가정 위에 짜여 있었다.

```java
q.setQuestionNo((int) row.getCell(colIdx++).getNumericCellValue());
```

문제번호 칸이 비어있거나 숫자가 아니면 `getNumericCellValue()`가 그대로 예외를 던지고, 그게 잡히지 않은 채 사용자에게는 500 에러 화면만 떨어졌다. "어느 행이 문제인지"도 알려주지 않는, 가장 불친절한 형태의 검증이었다.

## 2단계 — 관대하게 (파싱은 통과시키고, 저장 시 검증에 맡긴다)

고치면서 처음엔 "그럼 숫자 칸에 텍스트가 들어있으면 파싱 단계에서 막고 에러 메시지를 보여주자"는 식으로 접근했다. 그런데 이건 이 기능의 실제 구조를 생각하면 불필요하게 빡빡한 선택이었다. 엑셀을 업로드하면 바로 DB에 반영되는 게 아니라, **일단 화면(수정 가능한 그리드)에 올라가고, 거기서 사람이 확인/수정한 뒤 별도의 저장 버튼을 눌러야 실제로 반영되는 구조**였다. 즉 파싱 단계에서 엄격하게 막을 필요 없이, 이미 존재하는 저장 시점 검증에 맡기면 되는 거였다.

```java
// 파싱 단계에서는 형식을 엄격히 검사하지 않는다 — 숫자가 비었거나 잘못돼도 0으로 채워서
// 일단 화면(수정 가능한 표)에 올리고, 실제 검증은 저장 시(questionManage.html의 검증 로직)에 맡긴다.
private static double getNumericValue(Cell cell) {
    if (cell == null) return 0;
    return switch (cell.getCellType()) {
        case NUMERIC -> cell.getNumericCellValue();
        case STRING -> {
            try {
                yield Double.parseDouble(cell.getStringCellValue().trim());
            } catch (NumberFormatException e) {
                yield 0;
            }
        }
        default -> 0;
    };
}
```

숫자든 텍스트든 뭐가 들어있든, 파싱이 불가능하면 그냥 0으로 채워서 일단 화면에 올린다. 진짜 파일이 손상돼서 파싱 자체가 불가능한 극단적인 경우에만 에러를 보여주는 정도로 좁혔다. 이 시점에 함께, 보기(`option1~4`) 컬럼의 DB `NOT NULL` 제약도 별도 마이그레이션으로 풀었다 — 서비스 코드는 이미 빈 보기를 허용하도록 짜여 있었는데 스키마만 옛날 그대로 막고 있던, 코드와 스키마의 불일치였다.

## 3단계 — 부분적으로 다시 엄격하게 (단, 셀이 아니라 "파일 전체 구조"만)

관대한 정책으로 한동안 잘 굴러갔는데, 실제로 써보니 새로운 문제가 나타났다. 셀 단위로는 관대해도 괜찮았지만, **파일 전체가 애초에 잘못된 파일인 경우**까지 관대하게 받아주는 건 오히려 사고를 키우는 방향이었다. 예를 들면:

- 엑셀 파일 안의 행들이 서로 다른 시험 ID를 섞어서 담고 있는 경우
- 지금 열어놓은 화면의 시험과 완전히 다른 시험의 엑셀 파일을 잘못 올린 경우
- 문제 번호 자체가 통째로 비어있는(그리드 자체가 의미 없는) 경우

이런 경우는 편집 그리드로 넘겨서 사람이 하나씩 고치게 하기보다, **업로드 자체를 그 자리에서 막는** 게 맞는다는 판단이 섰다. 그래서 셀 단위 형식 관용은 유지한 채, 파일 전체의 구조적 정합성만 별도로 검사하는 메서드를 추가했다.

```java
/**
 * 엑셀 업로드 시 문제 단위 형식 검증(정답 형식 등)과 별개로,
 * 파일 전체 단위의 구조적 정합성만 확인한다. 시험 아이디가 뒤섞였거나,
 * 지금 열려 있는 화면의 시험과 다르거나, 문제 번호가 비어 있으면
 * 잘못된 파일을 그대로 업로드한 것일 가능성이 높아 편집 화면으로 넘기지 않고 바로 막는다.
 */
private String validateExcelBatch(List<ExamQuestionRequest> questions, Long targetExamId) {
    if (questions.isEmpty()) {
        return "엑셀 파일에 문제 데이터가 없습니다.";
    }
    if (questions.stream().anyMatch(q -> q.getQuestionNo() <= 0)) {
        return "문제 번호가 없는 행이 있습니다. 모든 행에 문제 번호를 입력해주세요.";
    }
    long distinctExamIds = questions.stream()
            .map(ExamQuestionRequest::getExamId).distinct().count();
    if (distinctExamIds > 1) {
        return "엑셀 파일 안의 시험 아이디가 서로 다릅니다. 하나의 시험에 대한 문제만 업로드해주세요.";
    }
    if (targetExamId != 0 && !targetExamId.equals(questions.get(0).getExamId())) {
        return "엑셀 파일의 시험 아이디(" + questions.get(0).getExamId()
                + ")가 현재 화면의 시험 아이디(" + targetExamId + ")와 다릅니다. 올바른 시험의 엑셀 파일인지 확인해주세요.";
    }
    return null;
}
```

## 정리 — "관대하게"의 기준을 다시 정의

세 단계를 거치면서 정착한 원칙은 이거다.

| 구분 | 기준 | 정책 |
|---|---|---|
| **셀 단위 형식** | 숫자칸에 텍스트, 빈 칸 등 개별 값의 형식 오류 | 관대하게 — 기본값으로 채워서 편집 화면으로 넘기고, 저장 시 검증에 맡김 |
| **배치 전체 구조** | 파일 내 시험ID 혼재, 화면 시험ID와 불일치, 문제번호 전체 누락 | 엄격하게 — 편집 화면으로 넘기지 않고 업로드 자체를 차단 |

"관대하게"는 셀 단위 형식 관용을 뜻하는 것이지, 파일 전체가 다른 시험 것이거나 뼈대(문제번호)가 아예 없는 경우까지 관대해야 한다는 뜻은 아니었다. 처음엔 이 구분 없이 "엄격 vs 관대"를 하나의 축으로만 생각했는데, 실제로는 **"셀 값의 형식"과 "파일 전체의 구조적 정합성"이 서로 다른 축**이라는 걸 세 번의 시행착오 끝에 알게 됐다.

## 교훈

- "가져오기 → 편집 그리드 → 저장" 3단계 구조를 가진 기능이라면, 굳이 가져오기(파싱) 단계에서부터 엄격하게 막을 이유가 없다. 어차피 사람이 그리드에서 확인/수정하고, 최종 저장 시점에 검증이 한 번 더 있기 때문이다.
- 다만 "관대함"에도 한계가 있다. 개별 값의 형식은 관대해도 되지만, 애초에 잘못된 파일(다른 대상의 데이터, 구조 자체가 깨진 경우)까지 편집 화면으로 넘기면, 사용자가 "이게 왜 이렇게 나오지?"부터 다시 헤매게 만든다. 이런 경우는 초입에서 바로 막아주는 게 오히려 친절하다.
- 검증 정책은 한 번에 정답이 안 나온다. 엄격 → 관대 → 부분적으로 다시 엄격, 이렇게 왔다 갔다 하면서 실제로 부딪혀본 뒤에야 "형식"과 "구조"라는 두 축을 구분해낼 수 있었다. 처음부터 완벽한 규칙을 세우려 하기보다, 실사용 피드백을 반영해서 조정해나가는 편이 결과적으로 더 나은 규칙에 도달했다.
