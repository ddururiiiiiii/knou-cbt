# PDF 자동화를 포기하고 수기 입력으로 전환한 이유

> 이 글의 일부는 커밋 활동 패턴으로 추론한 내용입니다. "왜 그만뒀는가"에 대한 실제 판단 근거(ROI 계산, 구체적으로 겪은 불편함 등)는 커밋 메시지에 남아있지 않아서, `[ ]`로 표시한 부분은 실제 기억으로 채워야 완결됩니다.

## 확인되는 사실 — 활동이 어느 시점에 멈췄다

`extractor/extract.py`(Claude API로 PDF에서 문제 추출)와 `extractor/upload.py`(추출된 JSON을 DB에 반영)는 2026-05-21(`ffc3a4e`, "Phase 2")에 처음 만들어졌다. 그 뒤로도 계속 손을 봤다 — `50d0ea6`(2026-07-30)에서 `upload.py`에 과목 구분 값(한글→enum) 매핑 로직을 추가한 게 마지막 수정이었다.

`git log -- extractor/` 기준으로 그 이후 이 디렉토리에는 커밋이 없다. 반면 같은 시기부터 수기 입력 경로(문제 등록/관리 화면)는 계속 활발하게 개선됐다.

```
d92d7c2  fix: 문제 이미지가 매 저장마다 사라지던 데이터 유실 버그 수정, 등록화면 UX 개선
34b3782  feat: 문제 관리 화면 UX 개선
a07b303  feat: 문제풀기 토스트, 엑셀 시험ID 검증, ...
```

즉 "PDF 자동 추출 파이프라인" 쪽 커밋은 멈췄고, "사람이 직접 입력/엑셀로 업로드하는 화면"은 계속 다듬어졌다. 두 경로가 같은 목적(문제 데이터를 늘리는 것)을 갖고 있었는데, 하나는 방치되고 하나는 계속 투자를 받은 셈이다.

## 정황상 짐작할 수 있는 이유

코드만 보고 짐작할 수 있는 것들:

- LLM 기반 추출은 결과를 사람이 검수해야 안심할 수 있는 구조였다(`extract.py`도 "upload.py로 업로드하기 전에 JSON 내용을 확인하세요"라고 스스로 경고한다). 검수를 건너뛸 수 없다면, 자동화가 아껴주는 시간은 "타이핑"뿐이고 "확인"에 들어가는 시간은 그대로 남는다.
- 과목 분류 값 형식이 안 맞아서 별도 마이그레이션(V5)까지 만들어 데이터를 정리해야 했던 사고(내부 DB 마이그레이션 기록 문서에도 남아있음)가 있었다 — 자동화 파이프라인이 만들어내는 데이터 품질에 대한 신뢰가 흔들렸을 가능성이 있다.
- 엑셀 업로드 경로(수기 입력의 배치 버전)가 오히려 계속 개선되면서, "엑셀에 붙여넣고 업로드"가 "PDF 스크립트 실행 → JSON 확인 → 업로드 스크립트 실행"보다 오히려 더 간단한 경로가 됐을 가능성도 있다.

## 빈칸

- [ ] 실제로 PDF 자동 추출을 몇 개 시험에 대해 써봤는지, 그중 몇 개나 검수 없이 그대로 쓸 만했는지
- [ ] Claude API 호출 비용이나 속도가 체감상 부담이었는지
- [ ] "이제 수기/엑셀로만 하자"고 명시적으로 결정한 순간이 있었는지, 아니면 자연스럽게 손이 안 가게 됐는지
- [ ] 앞으로 다시 자동화를 재개할 계획이 있는지, 있다면 어떤 부분을 다르게 할 것인지

## 교훈 (지금까지 확인된 부분만)

- 자동화 파이프라인은 "만드는 것"과 "계속 신뢰하며 쓰는 것"이 다른 문제다. 검수 없이는 못 믿는 자동화라면, 절약되는 시간이 생각보다 적을 수 있다.
- 두 개의 경로(자동화 vs 수기)를 동시에 유지보수하는 비용이 있다면, 실제로 어느 쪽에 시간을 계속 쓰고 있는지가 "이 프로젝트가 실제로 어느 쪽을 신뢰하는지"를 보여주는 가장 정직한 지표다. 커밋 로그가 말보다 정확했다.
