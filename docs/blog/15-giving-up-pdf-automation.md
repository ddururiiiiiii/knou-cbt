# PDF 자동화를 포기하고 수기 입력으로 전환한 이유

## 확정된 사실

2026-07-30, PDF 자동 추출 파이프라인(`extract.py`/`upload.py`)을 더 이상 쓰지 않고 **기출문제 데이터를 전부 수기로 직접 입력하기로** 결정했다. extractor 관련 작업(이미지 자동 업로드 등 추가 개선)도 그 시점부터 중단했다.

`extractor/extract.py`(Claude API로 PDF에서 문제 추출)와 `extractor/upload.py`(추출된 JSON을 DB에 반영)는 2026-05-21(Phase 2)에 처음 만들어졌고, 그 뒤로도 계속 손을 봤다. 이 결정이 내려진 뒤로는 `extractor/` 디렉토리에 커밋이 없다. 반면 같은 시점부터 수기 입력 경로(문제 등록/관리 화면, 엑셀 업로드)는 계속 활발하게 개선됐다 — 문제 이미지 유실 버그 수정, 엑셀 업로드 검증 강화, 로딩 스피너 추가 등.

## 같은 날 있었던 일 — 자동화 데이터의 품질 문제

이 결정이 내려진 바로 같은 날(2026-07-30), `subject_category` enum 불일치로 인한 운영 서버 500 에러를 고쳤다. 원인은 `extractor/upload.py`가 PDF에서 뽑아낸 한글 원문("전공필수", "교양선택" 등)을 정규화 없이 그대로 DB에 저장했는데, 애플리케이션 코드의 enum(`MAJOR`/`LIBERAL`/`ELECTIVE`)과 형식이 안 맞아서 화면 렌더링 단계에서 역직렬화가 실패했던 사고였다. 이미 잘못 들어간 데이터를 마이그레이션(V5)으로 정리하고, `upload.py`에도 매핑 로직을 급히 추가해 재발을 막았다.

같은 날 "자동화 파이프라인을 그만 쓰겠다"는 결정과 "그 파이프라인이 만든 데이터가 운영 장애를 냈다"는 사건이 겹친 건 우연으로 보기 어렵다. 다만 이 둘의 인과관계가 회고나 커밋 메시지로 명시적으로 남아있는 건 아니라서, "이 사고가 결정적 계기였다"라고 단정하기보다는 "신뢰가 흔들린 시점과 결정이 내려진 시점이 같았다" 정도로 정리하는 게 정확하다.

## 정황상 함께 작용했을 요인

- LLM 기반 추출은 결과를 사람이 반드시 검수해야 안심할 수 있는 구조였다. `extract.py`도 스스로 "upload.py로 업로드하기 전에 JSON 내용을 확인하세요"라고 경고한다. 검수를 건너뛸 수 없다면, 자동화가 아껴주는 건 "타이핑" 시간뿐이고 "확인" 시간은 그대로 남는다.
- 같은 시기 엑셀 업로드 경로(수기 입력의 배치 버전)가 계속 개선되면서, "엑셀에 붙여넣고 업로드"가 "PDF 스크립트 실행 → JSON 확인 → 업로드 스크립트 실행"보다 오히려 더 간단한 경로가 됐을 가능성도 있다.

## 그 이후

수기 입력 경로는 이후로도 계속 다듬어졌다 — 문제 이미지가 저장할 때마다 사라지던 버그 수정, 엑셀 업로드 시 배치 전체 구조 검증 추가, 로딩 스피너 등 UX 개선까지, 실제로 투자가 이어진 쪽은 수기/엑셀 경로였다. 이미 추출해둔 JSON 데이터(운영체제, 인공지능, 컴퓨터의이해 등 7개 시험분)는 자동화를 중단하기 전에 이미 DB에 반영이 끝난 상태였고, 그 이후의 데이터는 전부 수기로 채워졌다.

## 교훈

- 자동화 파이프라인은 "만드는 것"과 "계속 신뢰하며 쓰는 것"이 다른 문제다. 검수 없이는 못 믿는 자동화라면, 절약되는 시간이 생각보다 적을 수 있다.
- 데이터 품질 사고가 터진 시점과 "이 자동화를 그만 쓰겠다"는 결정 시점이 같은 날 나란히 기록돼 있다는 것 자체가, 커밋 로그와 운영 기록을 남겨두는 습관의 가치를 보여준다. 몇 달 뒤에 "왜 이걸 그만뒀더라"를 떠올리려 할 때, 그 순간의 기록이 없었다면 이 정황조차 재구성할 수 없었을 것이다.
- 두 개의 경로(자동화 vs 수기)를 동시에 유지보수할 이유가 없다고 판단되면, 하나를 과감히 접는 것도 선택이다. 계속 붙잡고 있는 것보다, 실제로 신뢰가 가는 쪽에 시간을 몰아주는 게 결과적으로 더 나은 데이터 품질로 이어졌다.
