# 개인 프로젝트에 Sentry 붙이기

## 문제

1인 개발로 서비스를 운영하다 보면 제일 무서운 게 "사용자가 에러를 겪었는데 나만 모르는 상황"이다. 로그를 서버에 쌓아봤자, 매일 SSH로 접속해서 로그 파일을 뒤지고 있을 순 없다. 에러가 나면 능동적으로 알림이 와야 한다.

그래서 Phase 0/1 정리 작업을 하면서 Sentry를 붙였다. `sentry-spring-boot-starter-jakarta` 의존성을 추가하고, `GlobalExceptionHandler`에 `@Slf4j` + `log.error`를 넣어서 운영 중 에러를 실제로 추적할 수 있게 만드는 게 목표였다.

## 붙이는 건 쉬웠는데 — 환경별로 설정이 다르다는 걸 놓쳤다

`build.gradle`에 의존성 한 줄, `application-dev.yml`에 DSN 설정 몇 줄로 로컬/개발 환경에서는 잘 동작했다.

```yaml
# application-dev.yml
sentry:
  dsn: ${SENTRY_DSN:}
  environment: dev
  traces-sample-rate: 0.1
```

그런데 나중에 배포 전 체크리스트를 정리하면서 각 환경별 설정을 표로 비교해보다가 이상한 걸 발견했다.

| 환경 | `sentry.dsn` | `environment` | `traces-sample-rate` |
|---|---|---|---|
| local | `""` (빈 값) | 미설정 | 미설정 |
| dev | `${SENTRY_DSN:}` | `dev` | `0.1` |
| **prod** | **설정 자체가 없음** | 미설정 | 미설정 |

`application-prod.yml`에는 Sentry 섹션이 통째로 빠져 있었다. dev 프로필로 개발하고 테스트할 땐 전혀 눈치챌 수 없는 문제다 — dev에서는 잘 되니까. 실제 운영 환경(prod)에서 에러가 터졌을 때 Sentry로 리포팅이 되는지는 **한 번도 검증한 적이 없었다.**

이게 딱 "로컬에서는 되는데" 계열의 함정이다. dev 프로필로 아무리 열심히 테스트해도 prod 프로필의 설정 누락은 절대 못 잡는다.

## 실제로 잡히는 범위도 생각보다 좁다

Sentry를 붙였다고 모든 에러가 다 잡히는 게 아니다. 이 프로젝트의 `GlobalExceptionHandler`는 상황별로 로그 레벨을 다르게 남기는데, Sentry는 기본적으로 `log.error`로 남긴 로그만 자동으로 리포팅한다.

| 상황 | 로그 레벨 | Sentry 리포팅 |
|---|---|---|
| 404 (존재하지 않는 리소스) | `warn` | 안 됨 |
| 403 (권한 없음) | `warn` | 안 됨 |
| 409 (삭제 충돌) | `warn` | 안 됨 |
| 400 (잘못된 입력) | `warn` | 안 됨 |
| 503 (점검 모드) | 없음 | 안 됨 |
| 그 외 모든 예외(500) | `error` | **잡힘** |

처음엔 "왜 이 에러는 Sentry에 안 뜨지?"하고 당황했는데, 생각해보면 당연한 설계였다. 사용자가 잘못된 파일을 올리거나 권한 없이 접근하는 건 "예상된 정상 처리 경로"고, 진짜 놀랄 만한 건 "예상 못 한 500"뿐이다. Sentry는 후자만 잡아주는 게 오히려 맞는 그림이었다. 다만 이 구분을 미리 알고 있지 않으면 "Sentry가 에러를 놓치고 있나?"하고 괜히 의심하게 되니, 팀(사실상 나 혼자지만) 내부 문서로 남겨둘 가치가 있었다.

## 해결(진행 중)

`application-prod.yml`에 dev와 동일한 패턴으로 Sentry 섹션을 추가하는 것 자체는 어렵지 않다.

```yaml
sentry:
  dsn: ${SENTRY_DSN}
  traces-sample-rate: 0.1   # 트래픽이 적은 초기엔 더 올려도 무방 (0.5~1.0)
  environment: prod
```

다만 이걸 추가한 뒤에도 "정말 되는지"는 실제로 운영 서버에서 에러를 하나 일부러 터뜨려보고 Sentry 대시보드에 뜨는지 확인해야 확신할 수 있다. 설정을 채워 넣는 것과, 그 설정이 실제로 동작하는지 확인하는 것은 다른 일이다.

## 교훈

- 여러 환경(local/dev/prod)으로 설정을 나누는 구조에서는, "새 설정을 dev에만 넣고 prod엔 깜빡했다"가 제일 흔한 실수다. 환경별 yml을 나란히 놓고 비교하는 습관이 없으면 이런 누락은 몇 달이 지나도 발견되지 않는다.
- 모니터링 도구를 "붙였다"와 "운영 환경에서 실제로 작동한다"는 별개의 명제다. 배포 전에 반드시 실제로 에러를 유발해서 대시보드에 찍히는 걸 눈으로 확인하는 단계를 체크리스트에 넣어야 한다.
- 에러 트래킹 도구가 "왜 이 에러는 안 잡지?"라고 헷갈리게 만든다면, 그건 도구의 결함이 아니라 애플리케이션의 로그 레벨 설계를 먼저 이해해야 하는 신호일 수 있다.
