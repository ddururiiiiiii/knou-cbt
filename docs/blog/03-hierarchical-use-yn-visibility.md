# 미사용으로 껐는데 왜 계속 보이지? — 계층적 노출 제어 설계기

## 문제

이 서비스는 학과 → 과목 → 시험이 3단 계층으로 이어진다. 각 단계마다 "사용여부"(`use_yn`)라는 토글이 있어서, 관리자가 아직 정리가 덜 된 학과나 과목, 오탈자가 많은 시험을 끌 수 있게 되어 있었다.

그런데 관리 화면을 손보다가 이상한 걸 발견했다. **과목 자체를 `use_yn = 'N'`으로 꺼놨는데, 그 밑에 달린 시험들은 여전히 사용자 목록 화면에 보였다.** 시험의 `use_yn`은 각각 `'Y'`였으니 개별적으로는 틀린 게 하나도 없었다. 다만 "과목이 꺼지면 그 밑의 시험도 당연히 안 보여야 하는 것 아닌가"라는 상식이 코드에는 반영되어 있지 않았을 뿐이다.

버그 리포트로 들어온 게 아니라 코드/쿼리를 들여다보다가 발견한 케이스였다. 조회 쿼리 어디에도 상위 계층의 `use_yn`을 확인하는 조건이 없었다.

## 설계 결정 — "위에서 하나 끄면 아래는 손대지 않고, 조회 시점에만 숨긴다"

고칠 방법은 크게 두 갈래였다.

| 방식 | 장점 | 단점 |
|---|---|---|
| 상위를 끌 때 하위 `use_yn`도 실제로 같이 UPDATE(전파) | 조회 쿼리가 단순해짐 | 나중에 상위를 다시 켜면, 하위 항목들의 "원래 상태"를 이미 잃어버린 상태라 복원이 안 됨 |
| **조회 시점에 3단 AND로 계산** | 각 계층의 `use_yn` 원본값이 항상 보존됨 | 쿼리가 join을 3단으로 타야 함 |

전파 방식은 언뜻 쉬워 보이지만 "이력 관리가 꼬인다"는 치명적인 단점이 있다. 학과를 껐다가 나중에 다시 켰을 때, 그 밑에 있던 시험 중 원래부터 개별적으로 꺼져 있던 것과 학과 때문에 같이 꺼졌던 것을 구분할 수가 없어진다. 그래서 조회 시점 계산 방식을 택했다.

```sql
<if test="onlyActive">
    AND e.use_yn = 'Y' AND s.use_yn = 'Y' AND d.use_yn = 'Y'
    AND EXISTS (SELECT 1 FROM exam_question eq WHERE eq.exam_id = e.id)
</if>
```

시험(`e`), 과목(`s`), 학과(`d`) 세 단계의 `use_yn`을 전부 `AND`로 묶고, 여기에 "문제가 실제로 1개 이상 등록돼 있는가"까지 네 번째 조건으로 추가했다. 문제를 하나도 안 채운 빈 시험이 사용자 목록에 뜨는 것도 막고 싶었기 때문이다.

## 관리자와 일반 사용자를 같은 쿼리로 — `onlyActive` 플래그 하나

새 API나 별도 조회 메서드를 만드는 대신, 기존 메서드에 `onlyActive` 파라미터 하나만 얹어서 관리자/일반 사용자를 분기했다.

```java
// ExamViewController.java
boolean isAdmin = SecurityUtils.isAdmin();
examService.listPage(..., !isAdmin);
```

관리자는 `onlyActive = false`가 되어 위 AND 조건 자체가 안 붙는다 — 꺼진 것까지 전부 보여야 관리가 가능하기 때문이다. 그 외(비회원 포함 일반 사용자)는 `onlyActive = true`가 되어 필터가 적용된다.

## 관리자 UX 보완 — "왜 안 보이지?" 방지

DB 필터링만 해두면 관리자 입장에서는 오히려 헷갈릴 수 있다. 시험은 분명 켜놨는데 사용자 화면엔 안 보이니, "설정이 잘못됐나?" 하고 착각하기 쉽다.

그래서 조회 결과에 상위 계층의 `use_yn` 값도 같이 내려주도록 했다.

```sql
SELECT ..., e.use_yn, s.use_yn AS subject_use_yn, d.use_yn AS department_use_yn, ...
```

관리자 화면에서는 이 값을 보고 "시험 자체는 켜져 있지만 상위 과목이 꺼져 있어서 실제로는 안 보임" 같은 상황을 경고 아이콘으로 표시한다. **DB 필터링(AND 조건)과 관리자 UX(경고 표시)를 분리**함으로써, 필터링 로직은 단순하게 유지하면서도 관리자가 헷갈리지 않게 만들었다.

## 교훈

- "상위가 꺼지면 하위도 안 보여야 한다"는 요구사항은 너무 당연해서 오히려 구현이 빠지기 쉽다. 각 계층을 독립적으로 개발하다 보면, 계층 간의 암묵적 규칙은 누구도 명시적으로 티켓을 만들지 않기 때문이다.
- 계층적 상태를 다룰 땐 "값을 전파해서 실제로 바꾸기"보다 "원본은 보존하고 조회 시점에 계산하기"가 되돌리기 쉽고 안전하다. 특히 사람이 껐다 켰다를 반복할 가능성이 있는 토글이라면 더더욱 그렇다.
- 필터링 로직(사용자가 뭘 보는가)과 설명 로직(관리자가 왜 그런지 아는가)은 굳이 하나로 합칠 필요가 없다. 오히려 분리해두면 각각이 단순해진다.
