# 로그인 방식 설계기 — 왜 세션을 선택했나

## 미리 밝혀두는 것

이 글은 "JWT를 써봤다가 세션으로 갈아탄" 극적인 전환기가 아니다. 실제로 커밋 히스토리를 다시 훑어봐도, 이 프로젝트에 JWT 관련 코드나 의존성, 심지어 "JWT를 검토했다"는 주석 한 줄조차 없다. 처음부터 끝까지 세션 기반 폼 로그인 하나로 쭉 왔다. 그래서 이 글은 "왜 JWT를 버렸나"가 아니라, "왜 애초에 세션이 자연스러운 선택이었나"를 코드 구조를 근거로 풀어보는 글이다.

## 이 서비스의 구조

`SecurityConfig`를 보면 인증 방식은 명확하다.

```java
http.formLogin(form -> form
        .loginPage("/admin/login")
        .defaultSuccessUrl("/")
        .permitAll()
    )
    .rememberMe(rememberMe -> rememberMe
        .key("knou-cbt-remember-key")
        .tokenValiditySeconds(14 * 24 * 60 * 60) // 14일
        .userDetailsService(customUserDetailsService)
    )
    .userDetailsService(customUserDetailsService);
```

폼 로그인 + 세션 + remember-me(14일 자동 로그인)라는, Spring Security 튜토리얼에 나오는 가장 기본적인 조합이다. `SessionCreationPolicy.STATELESS`도 없고, `Authorization: Bearer` 헤더를 파싱하는 필터도 없다.

## 왜 이게 자연스러웠는가

JWT가 빛을 발하는 상황은 보통 이렇다.

- 클라이언트가 서버와 물리적으로 분리된 SPA/모바일 앱이라 세션 쿠키를 공유하기 애매한 경우
- 여러 개의 마이크로서비스/API 게이트웨이가 있어서, 매 요청마다 세션 스토어에 접근하는 대신 토큰 자체에 인증 정보를 담아 전달하고 싶은 경우
- 인증 서버와 리소스 서버가 물리적으로 다른 경우

이 프로젝트는 세 조건 중 어느 것도 해당하지 않는다.

- **Thymeleaf 서버사이드 렌더링**이다. 브라우저가 HTML을 받아서 그리는 구조지, 별도의 프론트엔드 애플리케이션이 API를 호출하는 구조가 아니다.
- **단일 Spring Boot 서버** 하나가 전부다. API 게이트웨이도, 별도 인증 서버도, 마이크로서비스로 쪼개진 백엔드도 없다.
- 관리자와 일반 사용자 모두 **브라우저로만** 접근한다. 모바일 앱이나 외부 API 클라이언트가 존재하지 않는다.

이 조건에서 JWT를 도입한다면 얻는 게 거의 없다. 토큰을 브라우저 어딘가(로컬스토리지든 쿠키든)에 저장해야 하고, 만료·재발급·로그아웃 시 무효화 같은 것들을 직접 구현해야 하는데, 세션이라면 Spring Security가 이미 다 해준다. 오히려 JWT를 쓰면 "로그아웃해도 토큰 자체는 만료 전까지 여전히 유효하다"는, 세션에는 없는 골치 아픈 문제까지 새로 떠안게 된다.

## remember-me 14일 — 세션의 단점을 상쇄하는 선택

세션 방식의 흔한 불만은 "브라우저를 껐다 켜면 다시 로그인해야 한다"는 것이다. 이건 JWT의 장점처럼 소개되곤 하지만, 사실 Spring Security의 remember-me 기능으로도 충분히 해결된다. 로그인 시 자동 로그인을 체크하면 14일간 세션이 유지되도록 만들어서, 매번 재로그인해야 하는 불편함 없이도 세션의 단순함을 그대로 누릴 수 있게 했다.

## 만약 나중에 API 클라이언트가 생긴다면

이 구조가 영원히 맞는 건 아니다. 만약 나중에 모바일 앱이나 별도 SPA 프론트엔드가 추가된다면, 그때는 세션 쿠키 공유가 애매해지면서 토큰 기반 인증을 다시 검토해야 할 것이다. 하지만 "지금 없는 요구사항을 미리 상상해서 설계를 복잡하게 만들지 않는다"는 원칙에 따라, 그 결정은 실제로 그런 요구가 생겼을 때 내리는 게 맞다고 본다.

## 교훈

- 인증 방식 선택은 "요즘 트렌드가 뭔가"가 아니라 "클라이언트와 서버의 물리적 구조가 어떤가"로 결정해야 한다. SSR 단일 서버 구조에서는 세션이 복잡도가 가장 낮은 선택이다.
- "왜 이렇게 했는가"를 코드만 보고 재구성하려니, 실제로 고민한 흔적(커밋 메시지, 주석)이 없으면 사후적으로 "합리적이었을 것이다"라고 추론할 수밖에 없다는 걸 이번에 새삼 느꼈다. 중요한 아키텍처 결정은 그 순간에 한 줄이라도 이유를 남겨두는 습관이, 나중에 스스로도 "이게 왜 이렇게 돼있지?"라고 헷갈리지 않는 데 도움이 된다.
