# PDF 기출문제 자동 추출 파이프라인 만들기

## 문제

이 서비스의 핵심 콘텐츠는 방송통신대학교 기출문제다. 그런데 원본 자료는 대부분 PDF(간혹 HWP)로 흩어져 있고, 문제/보기/정답을 손으로 하나하나 옮겨 적는 건 규모가 커질수록 감당이 안 되는 일이었다. 문제 하나를 등록하려면 지문, 보기 4개, 정답까지 최소 6개 필드를 입력해야 하는데, 시험 하나에 문제가 수십 개씩이니 자동화 없이는 규모를 늘리기 어려웠다.

## 접근 — 규칙 기반 파싱 대신 LLM에 통째로 맡기기

PDF에서 텍스트를 뽑아 정규식이나 레이아웃 규칙으로 "몇 번 문제, 보기 ①②③④, 정답"을 파싱하는 전통적인 방법도 있었다. 하지만 방송대 기출문제 PDF는 스캔 품질, 표, 그림 설명이 섞여 있는 등 레이아웃이 제각각이라, 규칙 기반 파서를 만드는 비용이 오히려 더 클 것 같았다.

그래서 택한 방법은 PDF 파일을 통째로 Claude API(Haiku 모델)에 넘기고, "이런 JSON 구조로 뽑아달라"고 프롬프트로 지시하는 방식이었다.

```python
response = client.messages.create(
    model="claude-haiku-4-5-20251001",
    max_tokens=8192,
    messages=[{
        "role": "user",
        "content": [
            {"type": "document", "source": {
                "type": "base64", "media_type": "application/pdf", "data": pdf_data,
            }},
            {"type": "text", "text": PROMPT},
        ],
    }],
)
```

프롬프트는 원하는 JSON 스키마를 명시적으로 지정한다.

```
반드시 아래 형식의 순수 JSON만 반환하고, 다른 설명은 쓰지 마세요:
{
  "questions": [
    {
      "question_no": 1,
      "question_text": "문제 내용 전체",
      "option1": "보기 1 내용",
      ...
      "answer": 1
    }
  ]
}
```

이 방식의 장점은 명확했다. 레이아웃이 스캔본이든 표가 섞였든, 사람이 읽고 이해할 수 있는 수준이면 모델도 대체로 같은 방식으로 이해해서 구조화해준다. 정규식 기반 파서라면 PDF 하나마다 예외 케이스를 새로 추가해야 했을 텐데, 그럴 필요가 없었다.

## 파이프라인 — 추출과 업로드를 분리

`extract.py`가 PDF를 읽어 JSON 파일로 저장하고, `upload.py`가 그 JSON을 DB에 반영하는 두 단계로 나눴다.

```
extract.py  : PDF → Claude API → JSON 파일 (사람이 검수 가능한 중간 산출물)
upload.py   : JSON 파일 → DB (department/subject/exam get-or-create → exam_question INSERT)
```

두 단계를 합쳐서 "PDF 올리면 바로 DB에 반영"으로 만들 수도 있었지만, 일부러 중간에 JSON 파일이라는 검수 지점을 뒀다. `extract.py` 실행 후 콘솔에도 이렇게 안내한다.

```
저장 완료: {output_path}
upload.py로 DB에 업로드하기 전에 JSON 내용을 확인하세요.
```

LLM이 뽑아낸 결과를 무조건 신뢰하지 않고, 사람이 한 번 훑어볼 여지를 남긴 것이다. 특히 정답을 확신할 수 없는 문제는 `answer: null`로 비워두게끔 프롬프트에 명시해서, "모르면 틀리게 채우지 말고 비워두라"는 원칙을 세웠다.

## 놓쳤던 부분 — 값 형식 불일치

`upload.py`가 처음 만들어졌을 때는 과목 구분(`subject_category`) 같은 값을 한글 그대로("전공필수", "교양선택" 등) DB에 저장했다. 그런데 애플리케이션 코드의 enum은 `MAJOR` / `LIBERAL` / `ELECTIVE` 같은 영문 값을 기대하고 있었다. 이 파이프라인이 저장하는 값과 애플리케이션이 기대하는 값의 형식이 서로 안 맞았던 것이다.

결국 이미 잘못 들어간 데이터를 별도 마이그레이션으로 일괄 정리하고, `upload.py` 쪽에도 한글→영문 매핑 로직을 나중에 추가했다. 외부 파이프라인이 만들어내는 데이터와 애플리케이션이 기대하는 데이터의 "계약"을 처음부터 맞춰뒀어야 했는데, 파이프라인과 애플리케이션을 따로 만들다 보니 이 부분을 놓쳤다.

## 교훈

- 레이아웃이 일정하지 않은 문서에서 구조화된 데이터를 뽑아야 할 때, 규칙 기반 파서보다 LLM에 스키마를 지정해서 맡기는 쪽이 훨씬 적은 코드로 훨씬 넓은 케이스를 커버할 수 있었다.
- 자동 추출 결과를 자동으로 바로 반영하지 않고 "중간 검수 지점(JSON 파일)"을 둔 건 잘한 선택이었다. 특히 정답처럼 틀리면 곧바로 서비스 품질에 영향을 주는 필드는, 모델이 확신 없으면 비워두게 하고 사람이 채우게 하는 게 "그럴듯하게 틀린 값"보다 안전하다.
- 서로 다른 시스템(추출 스크립트와 웹 애플리케이션)이 같은 데이터를 주고받을 땐, 값의 "형식 계약"을 어느 한쪽 코드만 보고 짐작하면 안 된다는 걸 다시 배웠다. 이 사고는 나중에 별도의 DB 마이그레이션 기록으로도 남겼다.
