# 모니터링 도구 구성 (Sentry) — 2026-09-01 정식 운영 전환용

## 개요
- 현재 도입된 모니터링 도구: Sentry (`sentry-spring-boot-starter-jakarta 7.14.0`)
- 목적: 운영 중 발생하는 예외를 실시간으로 알아채기 위함
- 이 문서는 "지금 코드상 실제로 어떻게 동작하는지" + "배포 전 채워야 할 빈칸"으로 구성함

---

## 1. 환경별 설정 현황

| 환경 | sentry.dsn | environment 태그 | traces-sample-rate |
|---|---|---|---|
| local | `""` (빈 값, 사실상 비활성화) | 미설정 | 미설정 |
| dev | `${SENTRY_DSN:}` (환경변수 주입) | `dev` | `0.1` |
| prod | **설정 자체가 없음** | 미설정 | 미설정 |

- `application-prod.yml`에 sentry 섹션이 통째로 빠져있음
- Sentry SDK가 `SENTRY_DSN` 환경변수를 자체적으로 읽어서 yml 설정 없이도 동작할 가능성은 있지만, 확실하지 않음
- **[ ] 배포 전 확인 필수**: prod에서 일부러 에러 유발 후 실제로 Sentry 대시보드에 찍히는지 테스트
- **[ ] 확인 필요**: 안 찍히면 `application-prod.yml`에 아래 내용 추가
  ```yaml
  sentry:
    dsn: ${SENTRY_DSN}
    traces-sample-rate: 0.1   # 트래픽 적은 초기엔 더 높여도 무방 (예: 0.5~1.0)
    environment: prod
  ```

## 2. 실제로 Sentry에 잡히는 에러 범위

`GlobalExceptionHandler` 코드 기준으로 정리함.

| 상황 | 처리 방식 | Sentry 리포팅 여부 |
|---|---|---|
| 404 (존재하지 않는 리소스) | `log.warn` + error/404 화면 | ❌ 안 잡힘 (warn 레벨) |
| 403 (권한 없음) | `log.warn` + error/403 화면 | ❌ 안 잡힘 |
| 409 (삭제 충돌) | `log.warn` + error/409 화면 | ❌ 안 잡힘 |
| 400 (파일 타입/용량 오류) | `log.warn` + error/400 화면 | ❌ 안 잡힘 |
| 503 (점검 모드) | 화면만 노출, 로그 없음 | ❌ 안 잡힘 |
| 그 외 모든 예외 (500) | `log.error` + error/500 화면 | ✅ 잡힘 (ERROR 레벨 로그가 Sentry로 전달됨) |

- 즉, 지금 구조에서 Sentry는 **"예상 못 한 진짜 버그"만 잡아주는 용도**임
- 사용자가 잘못된 파일 올리거나 권한 없이 접근하는 건 "정상적으로 처리된 상황"이라 Sentry에 안 뜸 → 이건 의도한 설계라 문제 없음, 다만 "왜 특정 에러가 Sentry에 안 뜨지?" 헷갈리지 않기 위해 기록해둠

## 4. 운영 중 에러 알림 받았을 때 대응 절차

1. Sentry 알림에서 에러 발생 화면(URL), 스택트레이스, 발생 사용자 수 확인함
2. 재현 가능한 에러인지 먼저 직접 확인함 (같은 URL/조건으로 재현 시도)
3. 심각도 판단함
   - 전체 서비스 이용 불가 수준 → 즉시 핫픽스 또는 점검 모드 전환 고려
   - 특정 기능만 영향 → 다음 배포 사이클에 수정
4. 수정 완료 후 Sentry에서 해당 Issue를 "Resolved" 처리함
5. 반복되는 패턴이면 `docs/writing-topics.md` Tier 2(트러블슈팅 로그)에 기록 남김
