## 2. DB 복구(복원) 절차

- Supabase Dashboard에서 원하는 백업 시점 선택 후 복원 실행함
- [x] **로컬 Postgres로 리허설 완료 (2026-08-17)**: 예전에 받아뒀던 로컬 백업 파일(`db_cluster-21-09-2025@15-12-39.backup`, 2026-05-12 Phase 0 시점 — `pg_dumpall` 형식)을 새로 띄운 Docker Postgres 16 컨테이너에 `psql`로 복원함. Supabase 플랫폼 전용 객체(확장 `pg_graphql`/`supabase_vault`, `supabase_admin` 권한 부여 등) 관련 에러가 다수 찍히지만 전부 무해함(우리 앱과 무관한 Supabase 내부 스캐폴딩) — 실제 앱 스키마(`department`/`subject`/`exam`/`exam_question`/`exam_question_answer`/`notice`/`users`/`flyway_schema_history`)는 전부 정상 복원됨. 이 백업 시점엔 Flyway가 V1까지만 적용된 상태였는데, 복원된 DB에 애플리케이션을 `local` 프로필로 붙였더니 **Flyway가 V2~V8을 forward-fix 방식으로 전부 자동 적용**했고(`Successfully applied 7 migrations`), `/health`도 정상(`{"db":"OK","status":"UP"}`) 응답함 — "옛날 백업 + 최신 마이그레이션 재적용"이라는 실제 재해복구 시나리오가 문제없이 동작함을 확인함
- 복원 시 주의할 점
  - 복원 시점 이후에 쌓인 데이터(신규 응시 기록, 신규 회원 등)는 전부 사라짐 → 복원은 "최후의 수단"으로만 사용함
  - 복원 중에는 서비스가 불안정할 수 있으므로, 가능하면 점검 모드(`/admin/maintenance`)를 먼저 켜고 진행함
- 복구 후 확인 절차
  1. 주요 테이블 row 수 확인 (department, subject, exam, exam_question, users)
  2. 관리자 로그인 정상 동작 확인
  3. 시험 목록/응시 화면 정상 동작 확인
  4. 점검 모드 해제

## 3. Flyway 마이그레이션 롤백 원칙

- 현재 사용 중인 Flyway는 **자동으로 마이그레이션을 되돌리는 기능(Undo)이 없는 버전/구성**임
- 따라서 "V8을 취소한다" 같은 개념이 없고, 문제가 생기면 **새 마이그레이션 파일을 추가해서 앞으로 나아가며 고치는 방식(forward-fix)**을 원칙으로 함
  - 예: V8이 잘못됐으면 V8을 지우지 말고 V9에서 수정함
- 이미 운영 DB에 적용된 마이그레이션 파일(V1~V8)은 **절대 수정하지 않기** — Flyway가 체크섬으로 변경을 감지해서 배포 자체가 실패할 수 있음
- 데이터까지 되돌려야 하는 심각한 경우에만 위 1~2번(백업 복원)을 사용함

## 4. 애플리케이션(Render) 배포 롤백 절차

- [ ] Render 대시보드에서 "이전 배포로 되돌리기(Rollback/Redeploy previous)" 기능 위치 미리 확인해두기
- 절차
  1. Render 대시보드 > 서비스 > Deploys 탭 이동함
  2. 문제 생기기 직전, 정상 동작했던 배포(커밋) 확인함
  3. 해당 배포를 다시 배포(Redeploy)함
  4. 롤백 완료 후 스모크 테스트 체크리스트 중 핵심 항목(로그인, 시험 응시, 관리자 화면)만이라도 재확인함
- 주의: 코드만 롤백하고 DB 마이그레이션은 이미 적용된 상태로 남아있을 수 있음 → 코드 롤백과 DB 상태가 서로 맞는지(예: 새 컬럼을 쓰는 코드가 없어졌는데 컬럼은 남아있는 경우) 확인 필요함. 컬럼이 남아있는 것 자체는 대부분 문제 없음(이전 코드가 안 쓰는 컬럼일 뿐)
