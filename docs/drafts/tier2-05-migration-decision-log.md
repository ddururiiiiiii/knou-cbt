# DB 마이그레이션 의사결정 로그 (내부용)

## 개요
- Flyway로 관리 중인 마이그레이션(V1~V8)마다 "왜 이렇게 바꿨는지"를 정리함
- 다행히 마이그레이션 파일 자체에 이유가 주석으로 잘 남아있어서, 그걸 근거로 기록함
- 목적: 나중에 "이 컬럼은 왜 이런 타입이지?", "왜 이 제약을 뺐지?" 싶을 때 바로 찾아볼 수 있게

---

## 1. 전체 타임라인

```mermaid
flowchart LR
    V1["V1<br/>초기 스키마"] --> V2["V2<br/>문제 본문 TEXT화"]
    V2 --> V3["V3<br/>인덱스 추가"]
    V3 --> V4["V4<br/>보기 이미지 지원"]
    V4 --> V5["V5<br/>과목분류 값 정리"]
    V5 --> V6["V6<br/>다중학년+학기"]
    V6 --> V7["V7<br/>보기 NULL 허용"]
    V7 --> V8["V8<br/>운영설정 테이블"]
```

## 2. 요약 표

| 버전 | 변경 내용 | 왜 바꿨나 (한 줄) |
|---|---|---|
| V1 | 초기 스키마 생성 | 서비스 기본 테이블 구조 |
| V2 | `question_text` 컬럼을 TEXT로 변경 | 문제 본문 길이 제한에 안 걸리게 |
| V3 | 인덱스 3개 추가 (FK 컬럼들) | 조회 성능 개선 |
| V4 | `option_type`, `image_layout` 컬럼 추가 + 보기 길이 확장 | 텍스트 보기 외에 이미지 보기도 지원하기 위함 |
| V5 | `subject_category` 값 정리 | 한글 원문이 그대로 저장되어 enum과 안 맞던 데이터 정합성 문제 수정 |
| V6 | `grade` 타입 변경 + `semester` 컬럼 추가 + 유니크 제약 변경 | 한 과목이 여러 학년/학기에 개설되는 실제 케이스 반영 |
| V7 | 보기(`option1~4`) NOT NULL 제거 | 코드는 이미 빈 보기를 허용하는데 스키마만 막고 있던 불일치 해소 |
| V8 | `site_operation_setting` 테이블 생성 | 점검 모드/공지 배너 기능을 위한 싱글 로우 설정 테이블 |

## 3. V5 — 과목분류 값 정리 (데이터 정합성 문제)

- **문제**: 엑셀/PDF 추출 파이프라인(`extractor/upload.py`)이 한글 원문("전공필수", "교양선택" 등)을 그대로 DB에 저장함. 하지만 애플리케이션 코드의 `SubjectCategory` enum은 `MAJOR` / `LIBERAL` / `ELECTIVE` 영문 값을 기대함 → 화면에서 분류가 안 맞거나 필터링이 깨지는 문제로 이어짐
- **해결**: 이미 잘못 들어간 데이터를 UPDATE 문으로 일괄 매핑

  | 원본(한글) | 정리 후 |
  |---|---|
  | 전공필수, 전공선택, 전공 | `MAJOR` |
  | 교양필수, 교양선택, 교양 | `LIBERAL` |
  | 일반선택 | `ELECTIVE` |

- **교훈**: 외부 파이프라인(PDF 추출 등)이 저장하는 값과 애플리케이션이 기대하는 값의 형식을 맞추는 걸 별도로 검증해야 함. 지금은 데이터 정리로 땜빵했지만, 근본적으론 추출 파이프라인 쪽에서 저장 전에 변환하거나, DB에 CHECK 제약을 걸어서 애초에 잘못된 값이 못 들어오게 막는 것도 고려할 만함

---

## 4. V6 — 다중 학년/학기 지원 (요구사항 변경 대응)

- **문제**: 처음엔 과목의 `grade`가 단일 정수값이었는데, 실제로는 한 과목이 여러 학년(예: 1학년+3학년 동시 개설)에서 열리는 경우가 있었음
- **해결 방식 선택**
  - `grade`를 INT에서 콤마 구분 문자열("1,3")로 변경 — 이미 `exam_question.answers`(복수 정답)에서 쓰던 것과 같은 패턴을 재사용함
  - 별도 학년 테이블(정규화)로 쪼개는 대신 **콤마 문자열 방식을 택함** — 이미 검증된 패턴을 재사용해서 일관성 유지, 학년 조합이 자주 안 바뀌는 데이터라 정규화의 이점이 크지 않다고 판단
- **부수 변경**: `semester`(학기) 컬럼도 같이 추가함 — 한 과목은 항상 1학기 또는 2학기 중 하나로만 개설되므로 다중값 아닌 단일 컬럼으로 처리
- **유니크 제약 변경**: 과목명 전역 유일 → `(학과, 과목명, 학기)` 조합 유일로 변경. 학기가 다르면 같은 이름의 과목이 별도 행으로 존재할 수 있어야 하기 때문

## 5. V7 — 보기 NOT NULL 제거 (스키마-코드 불일치 해소)

- **문제**: `ExamQuestionServiceImpl.saveAll()`에서 빈 보기 값을 `blankToNull()`로 NULL 처리해서 저장하도록 이미 코드가 짜여 있었는데, DB 컬럼(`option1~4`)은 여전히 `NOT NULL`이었음 → 보기 4개를 다 못 채운 문제나 엑셀 업로드 시 빈 값 섞인 행을 저장하면 그대로 500 에러
- **해결**: 코드가 이미 "보기가 비어있을 수 있다"고 가정하고 있었으므로, 그 가정에 맞춰 스키마 쪽 제약을 완화함 (코드를 스키마에 맞추는 대신, 스키마를 코드 의도에 맞춤)
- **연결되는 소재**: 이런 "스키마는 NOT NULL인데 코드는 이미 nullable을 가정" 패턴이 또 있을 수 있어서, Tier 2의 "스키마-애플리케이션 로직 불일치 체크리스트" 항목에서 전수 점검 예정

---

## 6. 공통 원칙 (지금까지의 마이그레이션에서 드러난 패턴)

- 데이터 정합성 문제(V5)는 스키마 변경 없이 **UPDATE 문으로 기존 데이터만 정리**하는 방식 선호
- 스키마-코드 불일치(V7)는 **코드를 바꾸는 대신 스키마를 코드 의도에 맞춤** — 이미 코드가 배포되어 동작 중이면 스키마 쪽이 따라가는 게 안전
- 요구사항이 늘어날 때(V6) 정규화보다 **기존에 검증된 단순한 패턴(콤마 문자열)을 재사용**하는 쪽을 택함 — 오버엔지니어링 방지
- 모든 마이그레이션 파일에 "왜"를 주석으로 남기는 관례가 자연스럽게 자리잡음 → 앞으로도 유지할 것
